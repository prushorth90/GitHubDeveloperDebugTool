# Local read-only MCP server

Task 17 adds an opt-in MCP endpoint to the existing Spring Boot application.
It uses **official Java MCP SDK 2.1.0**, including its Jackson 3 mapper and
servlet-based **stateless Streamable HTTP** transport. This matches Java 21,
Spring Boot 4.1.1, Jakarta Servlet and Boot-managed Jackson 3.1.5 without a
Spring AI dependency, a second application, or changes to the AWS SDK/Bedrock
pipeline. MCP does not register REST analysis actions as tools.

## Local-only boundary

- Disabled by default (`app.mcp.enabled=false`). Enable with `MCP_ENABLED=true`.
- Only registered when the `local` profile is active and `prod` is **not** active.
- `POST /mcp` accepts MCP JSON-RPC; no session ID or server-side client session
  is created. `GET /mcp` is not an SSE subscription endpoint (405).
- A dedicated filter requires both the TCP peer and receiving interface to be
  loopback, a literal loopback/localhost Host, no `Forwarded`/`X-Forwarded-*`
  headers, and either no Origin or an exact same-origin HTTP Origin.
- Keep forwarded-header processing disabled. Do not expose through a reverse
  proxy, tunnel, container port mapping, or public listener. Run directly on the
  development host and bind the application to `127.0.0.1`.
- These restrictions are **not authentication**. Any local process can read any
  persisted repository. Authentication and repository-level authorization must
  be implemented before widening access. MCP is not deployed to Lambda; no CDK,
  Compose, frontend, webhook, queue, or deployment configuration is changed.

## Start locally

Use an existing initialized DynamoDB Local table with the
[read indexes and metadata migration](dynamodb.md#read-api-schema-and-migration).
MCP performs no table creation, migration, writes, GitHub requests, S3 downloads,
or model calls.

From the repository root, with DynamoDB Local listening on port 8000:

```sh
AWS_ACCESS_KEY_ID=local AWS_SECRET_ACCESS_KEY=local AWS_REGION=us-east-1 \
MCP_ENABLED=true SQS_WORKER_ENABLED=false BEDROCK_ENABLED=false \
DYNAMODB_ENDPOINT=http://127.0.0.1:8000 \
mvn -f backend/pom.xml spring-boot:run \
  -Dspring-boot.run.arguments="--spring.profiles.active=local --server.address=127.0.0.1 --server.port=18080"
```

Port 18080 avoids replacing an existing backend on 8080. The dummy credentials
are for DynamoDB Local only; do not use this command to connect to AWS. Supply
the existing table name with `DYNAMODB_TABLE_NAME` if it differs from
`workflow-analyses`. This command disables background work and model generation
only in this separate smoke-test process; it does not alter the working Bedrock
configuration. MCP retrieval also works when Bedrock is enabled, but never calls
the analysis service or Bedrock.

Confirm readiness:

```sh
curl --fail http://127.0.0.1:18080/actuator/health
```

## Connect a local MCP client

For VS Code, add this server entry to your local MCP configuration
(`.vscode/mcp.json`, not required or generated by this change):

```json
{
  "servers": {
    "local-ci-failures": {
      "type": "http",
      "url": "http://127.0.0.1:18080/mcp"
    }
  }
}
```

Start the server connection in VS Code, then use its tools in chat. Example:
“Use local-ci-failures to retrieve the five latest failures for repository ID
1421755810, then retrieve the stored diagnostic findings for the first failure.
Do not generate a new analysis.”

Repository IDs are numeric GitHub IDs, **not** `owner/repo`. Discover IDs using
the existing `GET /api/repositories?limit=20` REST API.

### Tools

All tools require positive integer `repositoryId`. Unknown arguments, nulls,
wrong types, fractional IDs, invalid enum values, and out-of-range numbers are
rejected. IDs must fit a signed Java `long`. Optional `attempt` must be a positive
Java `int`; omit it to select the latest persisted attempt.

| Tool | Additional arguments | Result in `structuredContent.data` |
| --- | --- | --- |
| `recent_workflow_failures` | `limit` (1-20, default 10), `category`, `nextToken` | Newest-first page of stored failure run summaries |
| `failure_analysis` | Required `runId`; optional `attempt`, `jobOffset` (0-100000, default 0), `jobLimit` (1-5, default 3) | Run metadata, bounded failed-job diagnostics and provenance |
| `similar_workflow_failures` | Required `runId`; optional `attempt`, `limit`, `category`, `nextToken` | Newest-first page sharing any exact stored fingerprint, excluding all attempts of the source run |
| `repository_failure_statistics` | None | Aggregate counts over all persisted attempts, available job categories and latest run |

`category` accepts the existing exact `FailureCategory` enum values; see
[REST pagination and filtering](analysis-api.md#pagination-order-and-filtering).
Lists examine a bounded database page, so filtering can produce an empty page
with a non-null `nextToken`. Follow tokens until null. Pass tokens unchanged with
the same repository, tool, category and source attempt. Statistics have a fixed
response shape but stream all repository pages; database read cost and latency
grow with history. They are not a snapshot or maintained aggregate.

Run metadata includes run ID, attempt, workflow name, branch, conclusion, URL,
creation/analysis timestamps, processing status, completeness and categories.
List tools return summaries; call `failure_analysis` on a selected result for
diagnostic findings, evidence and provenance.

Detail responses preserve `analysisSource`, `modelIdentifier`, `fallbackReason`,
category, confidence, fingerprint, diagnostic finding kinds and evidence line
references from persistence. They do not relabel Java/fallback/legacy findings as
Bedrock findings or invent missing analyses. Evidence line numbers refer to the
sanitized job log, not source files. Observation confidence describes literal
log presence, not the truth of a claim or proven root cause.

### Bounds and errors

- Request body: at most 16 KiB. Pagination token: at most 4096 characters.
- Detail: at most 5 jobs per response; `totalFailedJobs` and `nextJobOffset`
  support pagination within the selected attempt. Pin `attempt` while paging.
- Each job's analysis contains at most 10 findings, 10 top-level evidence lines,
  10 context lines, and 10 evidence lines per finding. Each analysis string,
  evidence text, job name and log message is limited to 1000 Java characters.
- A job's `truncated=true` explicitly indicates shortened/omitted content.
  Evidence line numbers are preserved. Excerpts are not full logs; the existing
  REST detail endpoint retains its full stored DTO.
- Serialized tool results, including both structured content and its JSON text
  mirror, are capped at **256 KiB** (excluding the small JSON-RPC envelope).
  Excess returns `RESPONSE_TOO_LARGE`, not partial success; try a smaller page.
  Oversized single-record metadata may still require inspecting the REST detail.
- Success includes `repositoryId`, `storage: "DYNAMODB"`, `readOnly: true`, and
  `data` in `structuredContent`, with an identical JSON text representation for
  clients that only consume text.
- Tool failures have `isError=true`. SDK schema validation failures include a
  native validation message in text content. Adapter/service failures also have
  `structuredContent.error: {code, message}`. Codes include `INVALID_ARGUMENT`,
  `BAD_REQUEST` (e.g. invalid cursor), `NOT_FOUND`, `CONFLICT` (pending/failed
  analysis or absent fingerprints), `SERVICE_UNAVAILABLE`, `INTERNAL_SERVER_ERROR`,
  `INTERNAL_ERROR` and `RESPONSE_TOO_LARGE`. Internal errors are logged and do not
  expose SDK exception details. Unknown tools produce a JSON-RPC protocol error.
- Missing job analyses remain null with their stored log status/message. A
  processing latest attempt returns a conflict, not an older cached success.

Logs and model explanations are untrusted data, never instructions. No DynamoDB
entities, processing tokens, leases, or S3 object keys are exposed.

### Direct protocol examples

A stateless endpoint can process these requests without a session header:

```sh
# Discover tools.
curl --fail http://127.0.0.1:18080/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

# Retrieve up to five stored failures.
curl --fail http://127.0.0.1:18080/mcp \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"recent_workflow_failures","arguments":{"repositoryId":1421755810,"limit":5}}}'
```

For details, call `failure_analysis` with `{"repositoryId":1421755810,"runId":42}`;
replace 42 with a persisted failure run ID. For similarity use
`similar_workflow_failures` with the same arguments. Statistics use
`repository_failure_statistics` with just `repositoryId`.

The compatible Java SDK client used by the automated tests:

```java
var transport = HttpClientStreamableHttpTransport.builder("http://127.0.0.1:18080")
        .endpoint("/mcp").openConnectionOnStartup(false).build();
var client = McpClient.sync(transport).requestTimeout(Duration.ofSeconds(30)).build();
try {
    client.initialize();
    var tools = client.listTools();
    var result = client.callTool(new McpSchema.CallToolRequest(
            "recent_workflow_failures", Map.of("repositoryId", 1421755810L, "limit", 5)));
    System.out.println(result.structuredContent());
} finally {
    client.closeGracefully();
}
```

Imports come from `io.modelcontextprotocol.client`, its `transport` package,
`io.modelcontextprotocol.spec.McpSchema`, `java.time.Duration`, and `java.util.Map`.

## Automated verification

The MCP integration test launches the **existing full Spring Boot application**
on a random loopback port, uses the official SDK HTTP client, and replaces only
the repository and analysis execution dependencies with mocks. The real
`FailureService` performs reads, validation, filtering, similarity and mapping.
Assertions verify no analysis/model invocation and no repository writes.
Separate DynamoDB Testcontainers integration tests exercise real persistence.

```sh
mvn -f backend/pom.xml \
  -Dtest=FailureMcpIntegrationTest,LocalMcpConfigurationTest,LocalMcpFilterTest test

mvn -f backend/pom.xml \
  -Dtest=FailureMcpIntegrationTest,LocalMcpConfigurationTest,LocalMcpFilterTest,FailureServiceTest,RepositoryControllerTest,WorkflowRunAnalysisIntegrationTest,ContextualFailureAnalyzerTest,BedrockConfigurationTest,GitHubWebhookControllerTest,WorkflowEventWorkerTest,ProductionConfigurationTest test

# Docker required; run after test compilation.
mvn -f backend/pom.xml -Dit.test=WorkflowAnalysisRepositoryIT \
  failsafe:integration-test failsafe:verify
```

Coverage includes discovery and read-only annotations, all tool invocations,
schema and numeric validation, pagination/cursor scope, detail/job pagination,
evidence/provenance and fallback preservation, unavailable analyses, missing and
processing runs, corrupt data, database failures, response limits, session-free
requests, unsupported streaming GET, production/default disablement, and
loopback/Host/Origin/proxy restrictions.
